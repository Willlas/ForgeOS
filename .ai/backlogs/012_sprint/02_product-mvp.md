# Epic 2 — Product framing and MVP definition

## Objective

Define the product mission and the real MVP boundary so the project is not described as larger than it is.

## User stories

### US-04: The product mission is explicit
**As a stakeholder**
**I want** a short mission statement for Aer
**so that** I understand the problem the project is solving.

**Acceptance criteria:**
- Mission is no longer than 4 lines.
- It clearly explains the user/problem/value.
- It distinguishes runtime from CLI and prototypes.

### US-05: The real MVP is defined
**As a technical lead**
**I want** a defensible MVP definition
**so that** the next milestone has a realistic scope.

**Acceptance criteria:**
- Essential features are clearly listed.
- Scope is explicit and narrow.
- The MVP excludes aspirational features.
- The MVP aligns with the validated runtime flow.

### US-06: Stable vs experimental is clearly classified
**As a contributor**
**I want** a clear classification of current maturity
**so that** I can distinguish what is usable from what is still exploratory.

**Acceptance criteria:**
- Each major component is labeled as stable, experimental, planned, or aspirational.
- The classification is visible in docs.
- It reduces confusion between code that works and code that is still prototype-level.

## Tasks

- Draft a short mission statement for Aer.
- Define the MVP scope for the next milestone.
- Separate stable from experimental areas.
- Update reading materials with the final classification model.
